# CacheBlend third arm

Runs the Security Validator through [CacheBlend](https://github.com/YaoJiayi/CacheBlend)
(EuroSys '25) on the same 90 secure-code tasks, to test whether the vulnerability
silencing effect is specific to KVCOMM's offset approximation or generic to lossy
KV reuse.

CacheBlend is a different mechanism for the same problem: chunks are prefilled
independently, K is re-rotated to new absolute positions, and only the
highest-deviation tokens (measured on V at layer 1) plus a forced-exact suffix
are recomputed. If silencing appears here too, the effect is not a KVCOMM
implementation detail. If it does not, the effect depends on the approximation
strategy — which is equally informative.

## What is and isn't modified

The **blend kernel is the authors' unmodified code**. All six defining
properties — chunk-independent prefill, RoPE re-rotation, layer-1 squared-L2 V
deviation, top-`recomp_ratio` selection over non-suffix tokens, forced-exact
suffix, full recompute of the selected set at layers ≥2 — live in
`vllm/attention/backends/xformers.py`, which is left byte-identical and
sha256-verified by `setup_cacheblend.sh`.

What we add is plumbing. The fork patches `llama.py` but ships a stock
`qwen2.py`, so Qwen models load and blending silently does nothing.
`patches/qwen2_cacheblend.patch` ports that same ~80-line patch to `qwen2.py`; it
was generated by diffing the fork's own `llama.py` against the pristine
`llama_org.py` it ships alongside.

Two deliberate departures from the upstream examples, both correctness fixes:

- **Token ids, not decoded text.** `example/blend_musique.py` decodes chunks back
  to strings, which lets the engine prepend a BOS (hence its `[1:len+1]`
  slicing) and makes the final prompt a re-encode of a decode. We pass
  `prompt_token_ids`, so the sequence is exact and the offsets vanish.
- **A real `suffix_len`.** Upstream computes `last_len = len([q_ids+s_end])` —
  the length of a *one-element list*, i.e. `1` — so its examples force a single
  token exact. That is the acknowledged `TODO (Jiayi): fix last len`. We pass the
  actual suffix token count.

## Why Llama-3.2-3B is excluded

Its corpus does not support a replayed comparison: 37/90 generations were
truncated at the token cap, 59/90 differ across kv points despite a dense greedy
generator, and only 22/90 prompts rebuild token-exactly — leaving **9–13
comparable cases per kv point** against Qwen-Coder-7B's 51–69. Separately, the
fork would need two upstream backports it lacks (llama3 RoPE scaling, tied
embeddings), and the tied-embedding gap fails *silently* by loading an
uninitialised `lm_head`. Report Llama as KVCOMM-only and say why.

## Chunking, and the two suffix configurations

The validator prompt is five segments: `A` (system + "The task is: "), `T`
(task), `B` (connector), `C` (generated code), `D` (NIST rubric + ask).

KVCOMM approximates the rubric's KV too — `kvcomm_engine.py:1015-1022` adds a
blended delta to the trailing prefix segment, keeping only layer 0 exact. The
"exact-prefilled" comment in `secure_code_common.py` is about token *ids*, not
KV. So mapping CacheBlend's forced-exact suffix onto the rubric would make it
strictly more faithful than KVCOMM and quietly rig the comparison. Hence two
configs:

| Config | Chunks | Suffix (forced exact) | Meaning |
|---|---|---|---|
| **B** `suffix_matched` (primary) | `A`, `T`, `B+C`, rubric | the ask (~27 tok) | rubric blended — the structurally fair analogue of KVCOMM |
| **A** `suffix_native` (secondary) | `A`, `T`, `B+C` | rubric + ask (~253 tok) | rubric exact — CacheBlend's canonical query-in-suffix usage |

Both run the identical token sequence; only the chunk/suffix boundary moves. If
A silences little and B silences a lot, the finding sharpens to *"silencing
appears when the rubric, not just the evidence, sits in approximated KV"* — a
claim about lossy reuse in judge pipelines generally.

## Recompute ratio grid

`recomp_ratio` is a plain dict field on the model, so sweeping it needs no patch.

- `r=0.00` — only the suffix is exact. The maximally lossy lower anchor; without
  it, low silencing could just mean a larger exact-token budget.
- `r=0.16` — CacheBlend's own default.
- `r=1.00` — **near-dense, not dense.** Every non-suffix token is recomputed at
  layers ≥2, but layers 0–1 still read chunk-local KV. That residual is what the
  self-test measures.

Do **not** map `r` onto KVCOMM's γ. They are not commensurable: γ gates *whether*
to reuse and moves the hit rate; `r` sets *how much* to recompute given reuse and
moves per-hit fidelity at constant coverage. Compare on measured TTFT and on
`exact_fraction`, both of which are logged per task in `blend_debug.json`.

## Where CacheBlend lives

CacheBlend itself is **not** in this repository (see `external/README.md`).
`setup_cacheblend.sh` clones the authors' fork at a pinned commit into
`external/CacheBlend` (override with `CACHEBLEND_ROOT` or the first argument) and
builds it in its own conda env. The sweep scripts locate this harness via
`HARNESS_ROOT` (default: the repository root).

## Files

| Path | Purpose |
|---|---|
| `setup_cacheblend.sh` | Clone the fork, apply the patch, verify the kernel is unmodified, build into its own conda env |
| `patches/qwen2_cacheblend.patch` | The `qwen2.py` plumbing port |
| `bench/prompt_builder.py` | Spec → chunks + suffix, asserting the partition reproduces `full_ids` on every build |
| `bench/artifacts.py` | Writers for KVCOMM's folder layout and `Latency.json` schema |
| `bench/blend_runner.py` | The runner, plus `--self-test` |

Results land in KVCOMM's own layout so `paper_metrics.py`, `timing_metrics.py`
and `compare_validation_reports.py` score both arms with identical code — no
metric difference can be blamed on a different analysis path. Blend is written as
`mode: "kv_reuse"` and full prefill as `mode: "dense_prefill"`, because that is
what those labels mean to the analysis: the approximate arm and its paired exact
reference.

## Running it

Prerequisites: `datasets/secure_code/validator_prompt_spec/*.json` must exist
(see `experiments/export_frozen_inputs.py` then
`experiments/export_validator_prompt_spec.py`).

```bash
# 1. Build the fork in its own env (20-40 min; CUDA kernels compile from source)
bash cacheblend/setup_cacheblend.sh            # clones into external/CacheBlend (or $CACHEBLEND_ROOT)

conda activate cacheblend
export VLLM_ATTENTION_BACKEND=XFORMERS

# 1b. Verify the environment. Every check here corresponds to a failure that is
#     otherwise silent or misreported.
python cacheblend/bench/check_env.py --model Qwen/Qwen2.5-Coder-7B-Instruct

# 2. Harness self-test. Do not skip: it separates plumbing bugs from
#    approximation loss, and everything downstream is meaningless if it fails.
python cacheblend/bench/blend_runner.py \
  --model Qwen/Qwen2.5-Coder-7B-Instruct \
  --spec datasets/secure_code/validator_prompt_spec/Qwen_Qwen2.5-Coder-7B-Instruct_prompt_spec.json \
  --self-test

# 3. Pilot on 3 tasks before committing GPU hours
bash cacheblend/run_sweep.sh --stage 1 --limit 3

# 4. Full stage 1: 2 models x r in {0.00, 0.16, 1.00}
bash cacheblend/run_sweep.sh --stage 1

# 5. Score with KVCOMM's own analysis, one cell at a time
python experiments/make_kv_view.py results/CacheBlendRun --all
for v in results/CacheBlendRun__view_*; do python experiments/paper_metrics.py "$v"; done
```

## Dependency pinning (why `pin_env.sh` exists)

The fork declares `transformers >= 4.40.0` with no upper bound and leaves `numpy`
unpinned. Resolved today that yields transformers 5.x and numpy 2.x against
torch 2.2.1, and both fail *indirectly*:

- transformers 5.x requires torch ≥ 2.4, so it **disables PyTorch support and
  continues**, printing only `Disabling PyTorch because PyTorch >= 2.4 is
  required but found 2.2.1`. It also rewrites configs to
  `rope_scaling={"rope_type": ...}`, which has no `"factor"` key — so the first
  hard error is `assert "factor" in rope_scaling` in `vllm/config.py`, naming
  neither transformers nor the real problem.
- numpy 2.x cannot load torch 2.2.1's compiled extensions: *"A module that was
  compiled using NumPy 1.x cannot be run in NumPy 2.2.6"*.

`setup_cacheblend.sh` now pins these automatically. For an environment that was
built before that, `bash cacheblend/pin_env.sh` fixes it in place without
recompiling the CUDA kernels.

**The self-test gate.** V2 asserts that blending a single chunk covering the
whole prompt reproduces the full prefill token-for-token — with one chunk there
is no missing cross-chunk information, so any difference is a plumbing bug, not
approximation. If V2 fails, stop. V3 reports `r=1.0` agreement, which is
expected to be high but not perfect for the layer-0/1 reason above.
